# ohos-bootstrap

Everything an agent cannot do for itself before it can build, sign, install and
drive a HAP on an OpenHarmony / HarmonyOS device. Most of it is one-off.

Two setups are covered:

- **local** — the device hangs off the same machine the container runs on. Only
  the signing material needs a human (DevEco Studio is Windows/macOS only).
- **remote** — a Windows workstation owns the USB device, the agent runs on a
  Linux server. Adds an SSH topology and, optionally, a file share.

## What genuinely needs a human

| Step | Why the agent can't | One-off |
|---|---|---|
| Developer mode + USB debugging on the device | physical taps in Settings | yes |
| Accept the "trust this computer" prompt | a dialog on the device's screen | yes, per host |
| Generate signing material in DevEco Studio | the IDE is Windows/macOS-only and there is no CLI for it | yes, per bundle name |
| Disable the lock screen / set screen timeout to max | Settings taps, and a locked screen blanks every screenshot | yes |
| Run the hdc server + SSH tunnel on the workstation | it is the machine with the cable | per boot |
| Fetch the OpenHarmony SDK / command-line tools | the download is account-gated | yes |
| Add a `udev` rule so hdc can claim the device | root on the host; local setups only | yes |
| Plug the device in, and unplug it when it wedges | — | as needed |

Everything else — SDK paths, signing config files, port forwards, installs,
`uitest`, log capture — the agent does itself.

## Signing is the one that actually blocks

Read @ohos-bootstrap/resources/signing.md before touching signing. The short
version:

- DevEco Studio's "Automatically generate signature" writes certificates and a
  keystore under `<USER HOME>/.ohos/config/`, and the **encrypted** passwords
  into the project's `build-profile.json5`. Both halves are needed.
- Signing material is tied to the **bundle name**, so each app needs its own
  run: `org.servo.servo` (servoshell) and `org.openharmonyrs.arkwebtest`
  (the ArkWeb test app) are separate.
- hvigor decrypts the passwords with key material it looks for at
  `<dir containing storeFile>/material/`. Keep `config/` intact — moving the
  `.p12` away from `material/` breaks signing with a misleading error.
- Servo's `hvigorfile.ts` injects a signing config from the path in
  `$SERVO_OHOS_SIGNING_CONFIG`, so nothing secret is committed.

Ask the user for two things: a zip of `~/.ohos` (or `C:\Users\<you>\.ohos`) and
the project's `build-profile.json5`. Then:

```shell
bash skills/ohos-bootstrap/resources/setup_signing.sh [zip] [build-profile.json5]
```

It finds the material inside the archive whatever it is rooted at, keeps any
previous `config/` as a timestamped backup, calls `install_signing.py`, and
re-runs the signing checks. Prompts for anything not passed as an argument;
`install_signing.py` is still there for scripted use.

Devcontainer *features* are the wrong hook for this — they run during the image
build, as root, before the mounts exist, so the workspace and the uploaded files
are not there, there is no terminal to prompt on, and anything written lands in
an image layer, which is not where a keystore belongs. Detection belongs in
`postStartCommand` (the workspace's `post-start.sh` warns when
`SERVO_OHOS_SIGNING_CONFIG` names a missing file), and the interactive part
belongs in the script above. A feature would be a reasonable way to install
*hdc* at a pinned version, which is a different problem.

## Sharing a folder from Windows

Read @ohos-bootstrap/resources/windows-share.md. This is a convenience, **not**
a requirement for file transfer — `hdc file send` and `recv` do their file I/O
in the client process, so a remote agent can send its own local files (measured,
see the remote-tunnel notes). Use a share for bulk staging: the signing bundle,
DevEco build output, `hstack` symbolication input, captures the user grabbed by
hand.

Note the container has no `CAP_SYS_ADMIN` and no `mount.cifs`: mount the share
on the Linux host and bind-mount the mountpoint into the container.

## Remote hdc topology

The model, where the forward has to end so that plain `hdc` works in the
container, and the rules are in @hdc/resources/remote-hdc.md. What the user runs
on the workstation, and why, is in @ohos-bootstrap/resources/remote-tunnel.md.
The traps, in the order they bite:

- The container cannot see the build server's loopback. Either the forward ends
  in the container (sshd in the container, or host networking), or it binds the
  bridge address — which sshd refuses **silently** without
  `GatewayPorts clientspecified` — and a relay in the container forwards to it.
- On a shared build server, 8710 is everyone's default port: use a per-user port
  and `OHOS_HDC_SERVER_PORT`.
- Client and server versions are compared as an exact string, and a mismatch
  fails with no output at all. `checkserver` skips the check on purpose, which
  is why it goes first.
- `hdc fport` / `rport` terminate on the machine running the **server**, so a
  forwarded device port (WebDriver, devtools) is not reachable from the agent's
  container without a second tunnel hop.

## Bootstrap order

1. Device: developer mode, USB debugging, trust prompt, lock screen off.
2. Workstation: `hdc -v`, then `hdc kill && hdc start`, and confirm
   `hdc list targets` locally before involving the network.
3. Get an hdc of the **same version** into the container. Windows and Linux
   binaries cannot be shared, so take both from one OpenHarmony SDK release;
   copy `toolchains/hdc` *and* `toolchains/libusb_shared.so` together.
4. Tunnel up (remote only), ending where the container's plain `hdc` finds it
   (@hdc/resources/remote-hdc.md), with `OHOS_HDC_SERVER_PORT` set to its port.
   Then `hdc checkserver`.
5. Signing material generated, uploaded, installed, `SERVO_OHOS_SIGNING_CONFIG`
   exported.
6. `./mach package --ohos --flavor=<default|harmonyos>` and install once, by
   hand, to prove the whole chain before letting the loop run.
7. Screen awake: see @servo/resources/ohos-keep-screen-awake.md.

Steps 2-4 are where the time goes; @ohos-bootstrap/resources/remote-tunnel.md
has the whole sequence with the failure modes.

## Verifying the environment

Run `resources/check_env.sh` inside the container. It checks the hdc client and
whether its version check is even compiled in, TCP reachability of the server,
the handshake and version pair, attached devices, every signing config's paths
and key material, and the SDK variables — and prints the specific remedy for
each failure rather than just a red line.

```shell
bash skills/ohos-bootstrap/resources/check_env.sh          # auto-detects <gateway>:8710
HDC_REMOTE=172.17.0.1:8710 bash .../check_env.sh           # or say where the server is
```

It exits non-zero if anything failed, so it also works as a preflight in a
script. Warnings (a plaintext signing password, an unset
`ARKWEB_TEST_SIGNING_CONFIG`) do not fail the run.

hvigor writes into the SDK directory, so it needs a **writable** SDK tree. When
the SDK is bind-mounted read-only, build a symlink farm (see the devcontainer's
`post-start.sh` for the working shape) and point `OHOS_BASE_SDK_HOME` at it.
